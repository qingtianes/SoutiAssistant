# 鸿蒙“读屏搜题”技术评估（更新）

## 当前结论

当前项目不能把鸿蒙读屏搜题标记为已完成，也不应该用静态悬浮窗代替它。

## SDK 中已确认的能力

当前 DevEco SDK 的 `@ohos.multimedia.media` 声明包含：

```text
media.createAVScreenCaptureRecorder()
AVScreenCaptureRecorder.init(...)
AVScreenCaptureRecorder.startRecording()
AVScreenCaptureRecorder.stopRecording()
```

该接口是“屏幕录制器”路径，配置中需要传入由应用创建并拥有写权限的文件描述符。它的直接产物是录制文件，而不是一个在 ArkTS 层可持续读取的 OCR 帧流。

SDK 还声明了系统级选择器相关的 `PickerMode`，但当前项目的 target SDK 与模拟器环境尚未证明该路径可以为普通应用提供稳定的逐帧图像读取。

## 为什么本阶段不盲写读屏

读屏搜题至少需要同时解决：

1. 用户授权和系统录屏确认；
2. 取得屏幕或目标窗口的连续图像帧；
3. 将帧交给系统 OCR；
4. 去重、分题、滚动窗口稳定和匹配输出；
5. 切换到后台/其他应用后的生命周期与权限恢复。

目前 SDK 静态声明只能证明“存在屏幕录制能力”，不能证明普通应用已经拥有实时 OCR 帧能力。没有真机证据时实现会很容易变成无法运行的假功能。

## 当前项目决策

- 本阶段不新增虚假的读屏按钮；
- 保留 `docs/READ_SCREEN_EVAL.md` 作为技术评估记录；
- 真机阶段先做最小探针：申请录屏授权、启动录屏、验证是否能拿到可处理的图像帧；
- 只有拿到稳定帧流后，才进入 OCR、分题和题库匹配；
- 如果系统只允许录制文件而不提供应用内帧流，则读屏搜题明确降级为“系统限制，鸿蒙版暂不支持”。

## 与图片 OCR、摄像头扫描的关系

图片 OCR 和摄像头扫描不依赖跨应用屏幕采集，因此仍按现有主链路推进。当前模拟器缺少系统 OCR 原生模块，相关识别必须在支持 OCR 的鸿蒙真机验证。
